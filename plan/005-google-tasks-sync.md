# plan/005-google-tasks-sync: Google ToDo リストとの同期

- 元: [spec/life-dashboard.md](../spec/life-dashboard.md) の変更 1(R29〜R34)、4.1 の「Google の鍵の扱い」、懸念 C11〜C13
- 状態: 承認済み(承認者: リポジトリオーナー、2026-11-23)
- 承認後、この内容を `plan/005-google-tasks-sync.md` としてコミットしてから実装に入る。

## Context
大学の課題はすべて Google ToDo リストにあり、使い続けたい(intent の追記)。spec の変更 1 で、選んだリストとの完全な双方向の同期に決まった。
同期はサーバー側で Google にアクセスする必要があり、Google の長期の鍵をサーバーに保管する(spec 4.1、C12)。また、サーバー側の関数(Edge Functions)を初めて使うため、その配信の仕組みもここで作る。

## 大きいので3段階に分け、段階ごとにコミットして確かめる
| 段階 | 内容 | 段階の終わりに確かめること |
|---|---|---|
| A | 配信の自動化: GitHub Actions からマイグレーションとサーバー側の関数を Supabase クラウドに適用する | 手で SQL を貼らずに、push だけでクラウドが更新される |
| B | 鍵の保管: ログイン時に Google の長期の鍵をサーバーに送り、暗号化して保管する | 再ログイン後、鍵が保管されている(サーバーのログで確認) |
| C | 同期: リストの選択、同期の処理、画面 | Google ToDo の課題がアプリに入り、完了などが双方向に反映される |

## あなたにお願いする準備(段階ごとに案内する)
- 段階 A: Supabase のアクセストークンとデータベースのパスワードを、GitHub の **Secrets** に登録する(この2つは本物の秘密なので Variables ではない)。
- 段階 B:
  - Supabase の Edge Functions の Secrets に、Google のクライアント ID とシークレット、鍵の暗号化用の鍵を登録する。暗号化用の鍵は、私が作り方を示し、あなたの手元で作る(私は値を見ない)。
  - Google Cloud で **Google Tasks API** を有効にする。
  - Google Auth Platform の「対象」で、公開ステータスを「**本番環境**」にする。テストのままだと長期の鍵が7日で切れるため。審査は不要で、警告画面は今までどおり出る。
  - アプリでログアウトして、もう一度ログインする(ToDo の許可を追加でもらうため)。

## 段階 A: 配信の自動化
- `.github/workflows/deploy.yml` に `supabase` ジョブを足す: `supabase link` → `supabase db push` → `supabase functions deploy`。秘密は GitHub の Secrets から読む。
- すでに手で適用した2つのマイグレーションは、初回だけ「適用済み」として記録する(`supabase migration repair`)。これをしないと、同じテーブルを作り直そうとして失敗する。
- `CLAUDE.md` の「本番へは手で SQL を貼る」を、「push で自動で適用される」に改める。

## 段階 B: 鍵の保管
- マイグレーション: `google_credentials` に、鍵が使えなくなった時刻の列を足す。
- 関数 `supabase/functions/google-token/`: ブラウザからログインユーザーの JWT と長期の鍵を受け取り、AES-GCM で暗号化して保管する。暗号化用の鍵は関数の Secrets から読む。
- ブラウザ(`src/data/supabase.ts`): ログイン直後に長期の鍵を受け取ったら、上の関数に送る。ログインのスコープに `https://www.googleapis.com/auth/tasks` を足す。

## 段階 C: 同期
- マイグレーション: `items` に `deleted_at`(削除の記録。削除を Google 側にも伝えるため)と `synced_at`(最後に同期した時刻)を足す。権限はテーブルごとに明示する(CLAUDE.md の規約)。
- 同期の判断を純粋な関数にする: `supabase/functions/_shared/sync.ts` の `planSync(...)`。アプリの項目、Google のタスク、リストの結びつきを受け取り、「どちらに何をするか」の一覧を返す。通信やデータベースには触れない。
  - Google 側だけが変わった → アプリに反映。アプリ側だけが変わった → Google に反映。両方変わった → あとから変更したほうを正とする(R32)。
  - 変わったかどうかは、Google 側は前回見た更新時刻との比較、アプリ側は `updated_at` と `synced_at` の比較で判断する。
  - 同期する内容は、タイトル、締め切り(日付)、完了の状態だけ(R30)。象限やブロックへの配置は Google に送らない。
  - アプリで作った項目は、領域に結びついたリスト、なければ既定のリストに作る。既定のリストが未設定なら Google に送らない(C11)。
- 関数 `supabase/functions/google-tasks/`: 「リストの一覧」と「同期の実行」の2つの操作。長期の鍵で短期の鍵を取り、Google Tasks API を呼び、`planSync` の結果を適用する。
- 画面: 設定の欄に「Google ToDo との同期」を作る。リストごとに、同期する/しない、結びつける領域、既定のリストを選べる。最後に同期した時刻と「今すぐ同期」ボタン。アプリを開いたときにも同期する(R34 の前半)。
- 削除済みの項目は、Inbox や今の画面に出さない。

やらない(後の plan に回す): 定期実行による同期(R34 の後半。締め切りの通知と一緒に作る)、「いつか/やらない」に移した項目の Google 側での扱い(C11 の後半)、項目の削除ボタン。

## テスト(C13 の方針どおり、ここは厚めにする)
`planSync` の単体テストを12件程度:
- Google にだけある → アプリに作る(領域はリストの結びつきから)
- アプリにだけある(Google の ID なし) → 結びついたリストに作る / 既定のリストに作る / 既定がなければ何もしない
- Google 側だけ変わった、アプリ側だけ変わった、両方変わって Google が新しい、両方変わってアプリが新しい
- Google で完了 → アプリで完了。アプリで完了 → Google で完了
- Google で削除 → アプリで削除の記録。アプリで削除の記録 → Google で削除
- 同期しないリストのタスクは無視する
- 2回続けて同期しても、2回目は何もしない(重複を作らない)

暗号化は、暗号化して復号すると元に戻ることと、別の鍵では復号できないことをテストする。データベースの権限のテストも足す。

## リスク
- **同期の不具合で課題が消える、重複する**: 最も重い。上のテストで押さえる。さらに、最初の同期の前に、Google ToDo の課題の件数を控えておいてもらい、同期後に一致するかを確かめる。
- **関数の配信の失敗**: 初めて使う仕組み。段階 A だけで先に確かめる。
- **鍵が漏れる**: 暗号化して保管し、ブラウザには返さない。関数のログに鍵を出さない。フックがコミットを止める。
- **Google の本番環境への切り替え**: 審査なしの本番環境は、利用者が100人までなら使える。個人用なので問題ない見込みだが、Google の方針は変わりうる。
- **サーバー側の関数をこの作業環境で動かせない**: 今は軽さのため、関数の実行環境を手元で起動していない。関数の中身は薄くし、判断は `planSync` に寄せて単体テストする。関数そのものは本番で確かめる。

## 選ばなかった案
- ブラウザだけで同期する: 長期の鍵をブラウザに置くことになり、C12 に反する。定期実行もできない。
- 同期の処理をデータベースの中(SQL)で書く: Google の API を呼べず、テストもしにくい。
- 1つの plan を3つに分ける: 段階を分けたので、1つの plan のまま、段階ごとに確かめる形にした。

## 証明(Proof)
- 段階ごと: `npm run lint`、`npm test`、`npm run build`、`npm run test:db` が通り、GitHub Actions の配信が成功する。
- 段階 A: 新しいマイグレーションが、手作業なしでクラウドに適用される。
- 段階 C(あなたの確認):
  - 「大学」のリストを学校に結びつけて同期すると、課題がすべてアプリに入る。件数が Google ToDo と一致する。2回同期しても増えない。
  - アプリで課題を「やった」にすると、Google ToDo でも完了になる。Google ToDo で完了にすると、アプリでも完了になる。
  - Google ToDo で締め切りを変えると、アプリにも反映される。
  - アプリで放り込んだ項目が、既定のリストに作られる。

## 計画からのずれ
- 段階 A: Supabase CLI の現行版(3.2.0)は、`migration repair` と `db push` の既定の対象が開発用(ローカル)になっていた。`--remote` を付けてクラウドを対象にした。あわせて、CI の CLI の版を開発環境と同じ 3.2.0 に固定した(`latest` だと、こうした挙動の変化を突然受けるため)。
- 段階 A: CI では確認の質問に答えられないため、`--yes` を付けた。アクセストークンには「API Key Secrets: read」がないため、CLI の版の確認が飛ばされるという警告が出るが、権限を広げずにそのままにした。
- 段階 A の結果: 3回目の実行で成功。手で適用済みの2つのマイグレーションを適用済みとして記録できた。
- 段階 B: lint の警告が plan/004 から残っていたことに気づいた(終了コードが 0 だったため見落としていた)。`App.tsx` のデータの読み直しを、`useCallback` の依存に頼らない形(版の番号を上げて読み直す)に直し、lint を `--deny-warnings` にして警告でも失敗するようにした。CLAUDE.md の「Claude が間違えやすいこと」に記録した。
- 段階 B: CORS の処理を `supabase/functions/_shared/http.ts` に切り出した(段階 C の関数でも使うため)。
- 段階 B の配信: マイグレーションは自動で適用された(段階 A の確認になった)。関数の配信が `--yes` なしで止まったため追加した。同じ間違いが2回目なので、CLAUDE.md に追記した。
- 段階 B: Google のログインを本番環境にするには、ホームページとプライバシーポリシーの URL が必要だった(計画の準備に書いていなかった)。`public/privacy.html` を足した。連絡先は、公開リポジトリに個人のメールアドレスを載せないよう、GitHub の Issues にした。
- 段階 C: Google で完了済みのタスクは、新しくは取り込まないことにした(過去の課題で Inbox が埋まり、P1 に反するため)。すでに取り込んだタスクの完了は、計画どおり双方向に反映する。
- 段階 C: 「同期のあとに利用者が変更したか」を正確に判断するため、同期の処理が `synced_at` を書いたときに `updated_at` と同じ時刻にそろえるトリガーを足した(サーバーの時計とデータベースの時計のずれで、変更ありと誤判定しないため)。データベースのテストを2件足した(計17件)。
- 段階 C: 領域の一覧を `src/domain/areas.ts` に切り出した(同期の設定の画面で使うため)。
- 段階 C: サーバー側の関数(`google-tasks`、`google-token`)の型チェックは、手元に Deno がないため行えていない。判断の処理は `_shared/sync.ts` に寄せて Vitest でテストし、関数そのものは本番で確かめる(計画のリスクどおり)。
- 段階 B の不具合: ログイン直後に長期の鍵をサーバーへ送る処理が、ログイン後にしか表示されない部品(SpikePanel)の中で登録されていたため、ログインの知らせを取りこぼしていた(plan/004 での画面の組み替えで混入)。登録を `src/data/supabase.ts` の読み込み時に移した。本番で `google_credentials` が空だったことで見つかった。
- 段階 B の不具合(2つ目): 本番で `google-token` が「permission denied for table google_credentials」で失敗した。Supabase クラウドでは service_role にもテーブルの権限が自動で付かないため。権限を明示するマイグレーションを足し、データベースのテストに2件足した(計19件)。plan/004 と同じ種類の間違いの2回目なので、CLAUDE.md に追記した。
