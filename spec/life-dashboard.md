# 人生を管理するダッシュボード: 要件と設計

- 元の intent: [intent/life-dashboard.md](../intent/life-dashboard.md)(受理済み、2026-11-22)
- 状態: ドラフト(プロダクトオーナーのレビュー待ち)
- 方針の出典: intent の Constraints と Context。組織のスキルはまだないため、intent の制約を方針として扱う。

## 1. 設計原則

intent の制約と、哲学者や思想家の考え方を、判断に迷ったときの基準としてまとめる。以降の要件はすべてこの原則に照らして決める。

| # | 原則 | 由来 |
|---|---|---|
| P1 | 全部はこなせない前提で設計する。リストは「選ぶための候補」であって「こなすべき全て」ではない | 制約: リストの余白。セネカ『人生の短さについて』、バークマン『限りある時間の使い方』 |
| P2 | 空いている時間を「埋めるべき穴」ではなく「価値のある余白」として見せる | 制約: 時間の余白。老子『道徳経』第11章「無用の用」(器は中が空いているから役に立つ) |
| P3 | 振り返りは事実を映すだけで、点数をつけない | 制約: 数値の合否で判定しない。ストア派の「自分の力が及ぶことに集中する」 |
| P4 | 重要だが緊急でないこと(第2象限)のための時間を、先に確保する | 4象限マトリックス(アイゼンハワー、コヴィー) |
| P5 | 入力の手間を最小にする。仕分けは後回しにしてよい | 使う場面: 思いついたときに放り込む |
| P6 | 個人ツールとして軽く作る | Context: 本番運用ではない |

## 2. 機能要件

### 2.1 放り込む(Inbox)
- R1: どの画面からでも、1行入力でタスクややりたいことを追加できる。
- R2: 音声入力は OS 標準の音声入力(スマホのキーボードのマイク、PC の音声入力)で行う。アプリ側の特別な実装はしない。
- R3: 追加時は領域も象限も選ばなくてよい。未分類のまま Inbox に入る(P5)。

### 2.2 仕分ける
- R4: 各項目に領域(仕事、スキル強化、学校、プライベート、新規ビジネス)と象限(緊急度と重要度の4象限)を付けられる。どちらも省略可能。
- R5: 4象限のマトリックス表示で、ドラッグや選択で象限を変えられる。
- R6: 「いつか/やらない」の置き場所を用意する。そこに移すことは失敗ではなく、選んだ結果として扱う(P1)。
- R7: 締め切りを任意で付けられる(学校の課題など)。

### 2.3 週の計画
- R8: 週末に次の週を計画する画面を持つ。1日を2〜3時間のブロック(既定は早朝、午前、昼、午後、夕方、夜の6つ)に分け、7日 × 6ブロックの枠に項目を置く。分単位の時刻は扱わない。
- R8a: ブロックの区切り時刻は設定で変えられる(授業や勤務の時間帯に合わせるため)。
- R9: Google カレンダーの予定を、同じ枠の上に読み取り専用で表示する。
- R10: 何も置かれていない枠を「余白」として目に見える形で表示する(P2)。
- R11: 計画で埋まった枠の割合が高くなったら、やわらかく知らせる(例: 「今週は余白が少なめです」)。ブロックはしない。
- R12: 第2象限の項目を、先に置くよう促す(P4)。

### 2.4 今日と今週を見る
- R13: スマホでの既定の画面は「今日」。今日の枠に置いた項目だけを表示し、Inbox や全体のリストは折りたたむ(P1)。
- R14: 項目をやった、一部やった、やらなかった、の3段階で記録できる。

### 2.5 振り返る
- R15: 週の振り返り画面で、象限別と領域別に、使った時間の概算を表示する。概算は、やった枠を1枠 = 1単位として数える(厳密な時間計測はしない)。
- R16: 振り返りの表示に、目標値、合否、赤や緑の評価色を使わない(P3)。
- R17: 自由記述のメモを残せる。やらなかった項目は、来週へ持ち越すか、「いつか/やらない」に移すかを選べる。

### 2.6 通知
アプリから働きかけてくれることは魅力だが、急かされる感覚は余白の制約と衝突する。そこで、通知は種類を絞り、すべて個別にオフにできるようにする。
- R20: 週の儀式の通知。週末に「振り返りと来週の計画」を促す。曜日と時刻は設定で変えられる。
- R21: 朝の通知。今日のブロックに置いた項目を知らせる。今日の計画がない日は、余白の日であることを肯定的に伝える。
- R22: 締め切りの通知。締め切りを付けた項目について、前日などに知らせる。
- R23: 通知の文面は命令形や警告の口調にしない。1日の通知数に上限を設ける。

### 2.7 哲学者や思想家の言葉
- R18: 週の振り返りと計画の画面に、その場面に合った短い言葉を1つ表示する。
- R19: 言葉は、出典(人物、著作)を確認できたものだけを収録する。目安は20〜40件。

## 3. 非機能要件
- N1: PC とスマホの両方のブラウザで使える。スマホではホーム画面に追加して使える(PWA)。
- N2: 利用者は本人1人。
- N3: PC とスマホの間でデータが同期される。
- N4: 個人データは本人の管理下に置く。

## 4. 設計

### 4.1 構成
- フロントエンドのみの PWA。静的ホスティング(GitHub Pages など)で配信する。
- 自前のサーバーは持たない(P6)。
- Google アカウントでログインする。カレンダーの読み取りと、データの保存の両方にこのログインを使う。

### 4.2 データの保存先
- 本人の Google ドライブの、アプリ専用の隠しフォルダ(appDataFolder)に JSON で保存する。
- 端末内(IndexedDB)にもコピーを持ち、オフラインでも見られるようにする。

### 4.3 データモデル(概要)
- Item: id、本文、領域(省略可)、象限(省略可)、締め切り(省略可)、状態(Inbox / 候補 / いつか・やらない / 完了)
- Slot: 週、曜日、ブロック(早朝、午前、昼、午後、夕方、夜)、置いた Item の一覧
- Settings: ブロックの区切り時刻、通知の設定
- Result: Slot と Item ごとの記録(やった / 一部 / やらなかった)
- WeeklyReview: 週、メモ、持ち越しの判断
- Quote: 本文、人物、著作、表示する場面

## 5. Open questions への回答

intent の未解決事項に、選択肢と推奨案で答える。最終判断はプロダクトオーナーが行う。

| # | 問い | 選択肢 | 推奨 |
|---|---|---|---|
| 1 | 「人生の優先順位が高いこと」の定義 | A: 第2象限(重要だが緊急でない)とみなす。B: 領域ごとに重みを別に持つ | **A**。仕組みが一つで済み、4象限の考え方とも一致する。領域ごとの重みは、使ってみて必要になったら足す |
| 2 | 使った時間の測り方 | A: カレンダーの予定から計算。B: 枠ごとの自己申告。C: タイマーで計測 | **B**。タイマーは監視されている感覚を生み、P3 と余白の制約に反する。ざっくりした枠の計画とも粒度が合う |
| 3 | Google カレンダーへの書き戻し | A: 読むだけ。B: 計画した枠を書き戻す | **A**。書き戻すとカレンダーが埋まって見え、P2 に反するおそれがある。ただし通知の実現方法(C6)によっては、専用カレンダーへの書き込みが必要になる |
| 4 | 音声入力の方法 | A: OS 標準の音声入力。B: アプリ独自の録音と、AI による自動仕分け | **A**。追加の実装も費用もいらない。AI による仕分けは API キーとサーバーが必要になり、P6 と衝突するため後回しにする |
| 5 | 個人データの保存先 | A: 端末内だけ。B: 自分の Google ドライブ。C: 外部のデータベースサービス | **B**。PC とスマホで同期でき、データは本人の Google アカウントに残る。カレンダーと同じログインで済む |
| 6 | 哲学者や思想家の考え方の取り入れ方 | A: クオートの表示だけ。B: 設計原則への反映だけ。C: 両方 | **C**。設計原則は1章、クオートは R18 と R19 で扱う |

## 6. 範囲外(最初の版ではやらない)
- AI による自動仕分けや提案
- Google カレンダーへの書き戻し
- 複数人での共有

## 7. 懸念事項

| # | 懸念 | 衝突している方針 | 対応案 |
|---|---|---|---|
| C1 | 週の計画という仕組みそのものが、がんじがらめの原因になりうる | 機能(週の計画) と 制約(余白、柔軟性) | 枠は朝、昼、夜の3つだけで、時刻は扱わない。計画しない週があってもよい作りにする。週の途中で気軽に項目を動かせるようにする |
| C2 | 時間の集計を見せると、点数のように感じられる | 成功の兆し(時間を振り返る) と 制約(合否で判定しない) | 目標値や評価色を出さない(R16)。数字より先に、やったことの一覧を見せる |
| C3 | 有名な言葉には、出典が誤っているものが多い。現代の著作からの引用は著作権にも配慮が要る | R18、R19 | 出典を確認できたものだけを収録する。存命や近年の著者は、短い引用にとどめるか、言い換えて出典を示す |
| C4 | Google のログイン設定(OAuth クライアントの作成、同意画面)に手間がかかる。個人用の未審査アプリでは、警告画面が出たり、ログインが頻繁に切れたりする可能性がある | 4.1 と 4.2 の構成 と P6(軽く作る) | Stage 3 の最初に、ログインの持続性だけを小さく試す。問題が大きければ、保存先の推奨を見直す |
| C5 | スマホでの音声入力の精度は OS に依存する | R2 | 入力後にすぐ直せる画面にする。精度の不満が大きければ、選択肢4の B を再検討する |
| C6 | 通知(R20〜R22)を出すには、何かがアプリの外から決まった時刻に知らせる必要がある。サーバーを持たない構成(4.1)と P6 では、これが実現できない | R20〜R22 と 4.1(サーバーを持たない) | 下の「通知の実現方法」から選ぶ |

### 通知の実現方法(C6 の選択肢)

| 案 | 仕組み | 良い点 | 悪い点 |
|---|---|---|---|
| A | アプリが Google カレンダーに、通知専用のカレンダーを作り、儀式、朝、締め切りの予定を書き込む。通知はスマホや PC のカレンダーアプリが出す | サーバー不要。スマホでも PC でも確実に届く | カレンダーへの書き込み権限が必要になる。カレンダーアプリに予定が増える(専用カレンダーなので表示は切り替えられる) |
| B | 小さなサーバーレス関数を定期実行し、Web Push でアプリの通知を送る | アプリ自身の通知になり、文面や動きを細かく作れる | サーバーの運用が必要になる。関数が個人データを読む必要がある。iPhone ではホーム画面に追加した場合だけ届く |

推奨は **A**。軽く作るという前提(P6)を守れて、届く確実さも高い。
